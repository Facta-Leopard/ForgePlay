# ForgePlay compatibility catalog consumer contract

## 목적과 공개 주소

`site-data/compatibility-games.json`은 홈페이지와 ForgePlay 앱이 함께 읽는
공개 호환성 카탈로그다.

공개 URL:

`https://facta-leopard.github.io/ForgePlay/site-data/compatibility-games.json`

이 파일은 앱 바이너리의 최신 버전을 알리는
`site-data/current-release.json`과 책임이 다르다. 호환성 DB 갱신 결과로 앱
업데이트 여부를 판단하거나, 앱 릴리스 갱신으로 호환성 캐시를 덮어쓰면 안 된다.

## 소비자 동작

앱은 번들에 포함된 스냅샷을 항상 사용할 수 있는 기준 자료로 보관하고, 사용자가
명시적으로 갱신을 요청할 때만 공개 URL을 확인한다.

1. 앱 시작 시 유효한 캐시가 번들 스냅샷보다 새로우면 캐시를 사용한다.
2. 캐시가 없거나 손상됐거나 오래됐으면 번들 스냅샷을 사용한다.
3. 수동 갱신은 HTTPS의 정확한 공식 URL에서 JSON을 새로 받는다.
4. 응답 전체를 검증한 뒤에만 캐시를 원자적으로 교체한다.
5. 네트워크·HTTP·크기·JSON·스키마·내용·저장 검증이 실패하면 현재 목록을
   그대로 유지하고 실패 사실을 사용자에게 알린다.

원격 요청은 공유 캐시, 쿠키와 자격 증명을 사용하지 않는다. 리디렉션을 따르지
않고, 최종 URL이 공식 주소와 정확히 일치하는지 확인한다. 요청에는
`Accept: application/json`을 보내며 현재 응답 크기 상한은 2 MiB다.

## 데이터 검증

앱 소비자는 현재 카탈로그 `schemaVersion` 1과 2를 지원한다. 최소한 다음을
검증한다.

- 허용된 최상위 필드와 각 레코드 필드
- `updatedAt`의 `YYYY-MM-DD` 형식
- 컬렉션별 최대 개수와 전체 응답 크기
- 게임·기기·제보 ID의 형식과 중복
- 게임과 테스트 기기 참조의 무결성
- 상태, 출처, 차단 사유 및 다국어 텍스트
- 선택 필드의 형식과 길이

사이트의 `compatibility.schema.json`과 정적 검증은 앱이 허용하는 범위보다
느슨해지면 안 된다. 새 필드를 추가할 때는 사이트 스키마, 정적 검증, 앱
디코더와 앱 테스트를 같은 변경 단위로 갱신한다.

## 현재 리비전 규칙

현재 앱은 `updatedAt`과 검증된 JSON payload의 SHA-256을 함께 사용한다.

| 원격 자료 | 처리 |
| --- | --- |
| 현재보다 새로운 `updatedAt` | 검증 후 적용 |
| 같은 `updatedAt`, 같은 payload | 현재 자료 유지 |
| 같은 `updatedAt`, 다른 payload | 리비전 충돌로 거부 |
| 현재보다 오래된 `updatedAt` | 롤백으로 거부 |

따라서 현재 계약에서는 한 번 공개한 `updatedAt`의 내용을 바꾸지 않는다.
같은 날 들어온 여러 제보는 한 번의 DB 배포로 묶어야 한다. 날짜 하나에 서로
다른 payload를 연속 배포하면 이미 첫 payload를 받은 앱은 다음 payload를
적용하지 않는다.

하루에 여러 차례 독립적으로 배포해야 한다면 날짜를 임의로 앞당기지 않는다.
대신 향후 스키마에 단조 증가하는 `catalogRevision`을 도입하고, 앱 소비자와
사이트 스키마를 함께 지원한 뒤 전환한다. 앱 지원보다 먼저 새 필드를 공개하면
기존 앱이 DB 전체를 거부할 수 있다.

## 호환성 DB 게시 절차

1. 새 제보를 기존 ID와 병합하고 다국어 제목·비고를 검수한다.
2. 해당 날짜에 아직 공개하지 않은 하나의 `updatedAt`을 사용한다.
3. `compatibility-games.json`만 변경하고 스키마와 정적 사이트 검증을 실행한다.
4. GitHub Pages 배포가 끝난 뒤 공개 URL의 HTTP 상태, JSON MIME, 크기와
   payload 해시를 확인한다.
5. 앱에서 번들 자료 로드, 새 자료 갱신, 동일 자료 재확인, 오프라인 실패 및
   손상 자료 거부 흐름을 검증한다.

호환성 데이터 변경은 프로젝트 공지로 만들지 않는다. 홈페이지의 호환성 수와
호환성 페이지, 앱 카탈로그가 같은 JSON에서 결과를 읽는다.

## 최소 회귀 검증

- schema 1 번들 자료에서 schema 2 원격 자료로 갱신
- 같은 리비전과 같은 payload 재확인
- 같은 날짜의 다른 payload 거부와 기존 캐시 보존
- 오래된 원격 자료의 롤백 거부
- 잘못된 필드, 중복 ID와 끊어진 참조 거부
- 리디렉션, HTTP 오류, 초과 크기, 오프라인과 취소
- 캐시 쓰기 실패 시 이전 파일 보존
- 동시에 두 갱신이 실행될 때 한 개의 일관된 결과 유지
